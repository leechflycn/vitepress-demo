# 先 Skill 后 Agent：为什么 AI 工作流不能只靠一个聪明模型

很多人第一次接触 AI Agent，都会有一个很自然的期待：

只要模型足够聪明，事情是不是就能自动完成？

给它一个目标，让它自己拆任务、查资料、写代码、调用工具、总结结果。听起来很美好，也确实是很多 AI 产品宣传里的画面。

但真正把 Agent 放进日常工作流以后，很快就会发现：

**一个聪明模型，不等于一个可靠系统。**

模型可以生成内容，可以理解指令，可以临时推理。但如果没有流程、权限、输入输出标准、失败边界和人工确认机制，它越能干，反而越容易把事情弄乱。

这也是我越来越认同的一句话：

**先 Skill，后 Agent。**

这里的 Skill，不只是某个产品里的插件能力，而是把人的经验、流程和边界写成可复用规则的方式。

## 1. Agent 失败，常常不是模型不够强

很多 Agent 项目看起来失败，是因为模型没完成任务。

但拆开看，根因往往不是模型太笨，而是任务本身没有被组织好。

比如你让一个 Agent “每天帮我做内容生产”。这句话听起来明确，其实里面藏了很多未定义的问题：

- 新闻源从哪里来？
- 哪些来源可信，哪些只能当线索？
- 热点怎么筛？
- 什么叫值得写？
- 公众号和博客是不是同一篇？
- 谁负责事实核查？
- 谁负责最终观点？
- 哪些内容不能自动发布？
- 如果搜索失败，要不要硬凑？
- 如果资料不足，要不要停？

这些问题如果不提前写清楚，就算模型再强，也只能边做边猜。

而“边做边猜”就是失控的开始。

今天猜对了，你觉得 Agent 很聪明；明天猜错了，它可能就把低质量内容发出去，或者在错误信息上继续加工，甚至把一个本该暂停的任务强行推进。

所以 Agent 真正需要的，不只是更强的模型，而是一套明确的工作边界。

## 2. Skill 是把经验写成可执行流程

这里说的 Skill，本质是一种方法论：

**把一个任务从模糊愿望，拆成可重复执行、可检查、可交接的流程。**

一个好的 Skill 至少要回答五件事：

1. 什么时候使用它；
2. 输入需要什么；
3. 处理步骤是什么；
4. 输出应该长什么样；
5. 遇到风险或失败时怎么停。

比如“写热点文章”这个任务，如果没有 Skill，它可能只是：

“看到热点就写一篇。”

但有了 Skill，它会变成：

- 先收集新闻池；
- 标注来源、摘要、风险、传播迹象；
- 等主编选题；
- 做事实审核和写作价值审核；
- 再写母稿；
- 再适配公众号、博客或短视频；
- 发布前必须人工确认；
- 来源不足就标记观察，不硬写。

这时候 Agent 才不是在“自由发挥”，而是在执行一套明确的编辑流程。

这就是 Skill 的价值：

**它把人的经验，从脑子里拿出来，写成机器可以遵守的规则。**

## 3. 为什么要先 Skill，后 Agent

因为 Agent 擅长执行和组合，但不擅长替你定义责任。

如果你没有 Skill，Agent 会面对一个模糊世界：它不知道什么算完成，不知道谁能拍板，不知道失败几次该停，不知道哪些动作需要确认。

如果你先有 Skill，Agent 就有了轨道：

- 它知道该查什么；
- 知道先后顺序；
- 知道什么结果能交付；
- 知道哪些地方必须停下来问人；
- 知道失败不能无限重试；
- 知道外部发布不能擅自执行。

这时候 Agent 的能力才会变成生产力，而不是随机性。

很多人上来就追求“全自动 Agent”，其实顺序反了。

正确顺序应该是：

**先把任务写成 SOP，再把 SOP 变成 Skill，最后才让 Agent 去执行。**

## 4. 一个家庭 AI 工作室的例子

拿一个家庭 AI 工作室的内容生产线举例。

表面上看，这是一个简单需求：每天根据热点写文章。

但真正跑起来，它至少包含几个角色：

- 人类主编负责选题和最终确认；
- 主写 Agent 负责结构、观点和成稿；
- 资料 Agent 负责补来源、核事实、检查风险表达；
- 定时任务负责每天产出新闻池；
- 发布动作必须经过确认，不能自动对外发。

如果没有这些分工，任务很容易混成一团：

今天谁来选题？谁来核查？谁来写？谁来判断能不能发布？失败了谁负责？

一旦责任不清，Agent 之间就会互相甩锅，或者把协调成本推回给人。

但把流程写清楚以后，系统就稳定多了：

1. 定时任务先产出候选热点；
2. 人类主编从候选里拍板；
3. 主写 Agent 做选题审核和文章结构；
4. 资料 Agent 补官方来源和风险表达；
5. 主写 Agent 写成稿；
6. 发布前再等确认。

这不是因为某一个模型突然变神了，而是因为流程把“谁做什么、做到哪里、什么时候停”说清楚了。

这就是先 Skill 后 Agent 的实际意义。

## 5. Skill 还负责给 Agent 装刹车

很多人只关注 Agent 能做什么，却忽略了它不能做什么。

但真正可靠的自动化，最重要的不是油门，而是刹车。

一个成熟的 Skill 必须写清楚：

- 失败几次必须停止；
- 哪些动作需要人工确认；
- 哪些信息不能外发；
- 哪些来源不足时不能继续；
- 哪些任务不能自动发布；
- 哪些风险内容只能做素材，不适合成文。

比如内容生产里，AI 可以帮忙查资料、写草稿、做结构，但不能替人最终发表观点。尤其是公众号、博客、公开平台发布，必须有明确确认和预检。

再比如运维任务里，AI 可以读日志、分析问题、提出方案，但涉及删除、改配置、停服务，就必须先确认。

这不是保守，而是工程常识。

**没有刹车的 Agent，不叫自动化，叫风险放大器。**

## 6. 好的 Agent 系统，本质是组织设计

很多关于 Agentic AI 的讨论都会提到一个问题：企业想引入 AI Agent，但组织流程、权限、数据和协作方式没有准备好。

这说明 Agent 不是单纯的工具问题，而是组织设计问题。

哪怕是一个很小的家庭 AI 工作室，也一样需要组织设计：

- 谁是 owner；
- 谁能确认；
- 谁能执行；
- 谁只负责补资料；
- 哪些任务能自动化；
- 哪些任务必须人工拍板；
- 产物写到哪里；
- 失败怎么记录。

这些东西听起来不像 AI，反而像管理。

但越是 AI 工作流，越需要这种管理。

因为模型能力越强，能触碰的事情越多；能触碰的事情越多，就越需要权限、边界和复盘。

## 7. 怎么开始做自己的 Skill

如果你也想搭一个可靠的 AI 工作流，不要一开始就问“我要用哪个 Agent 平台”。

先拿一件具体任务，写一张 Skill 卡。

可以从这几个问题开始：

1. 这个任务什么时候触发？
2. 输入从哪里来？
3. 哪些信息必须核验？
4. 输出格式是什么？
5. 谁负责最终确认？
6. 哪些动作不能自动做？
7. 失败几次必须停？
8. 结果写到哪里，方便下次接续？

写完以后，再让 Agent 按这个流程执行。

你会发现，同一个模型，在没有 Skill 和有 Skill 的情况下，表现会完全不同。

没有 Skill，它像一个聪明但容易跑偏的实习生。

有了 Skill，它才像一个知道岗位职责、交付标准和红线的协作者。

## 结语：先有轨道，再谈自动驾驶

未来 AI Agent 肯定会越来越强。

但越强的 Agent，越不能只靠“聪明”运行。

真正能长期工作的 AI 系统，不是把所有事情丢给一个模型，而是把人的经验、流程、边界和判断，先沉淀成 Skill，再交给 Agent 去执行。

所以我更愿意把 Agent 看成发动机，把 Skill 看成道路、交通规则和刹车系统。

只有发动机，没有道路，跑不远。

只有聪明模型，没有流程设计，也成不了可靠工作流。

**先 Skill 后 Agent，本质上不是技术保守，而是把 AI 从玩具变成生产系统的必经步骤。**
